# Team 827: possession from automatic tracking

More Than A Hack 2027, Phase 1. This document explains how `827.csv` was made. Every frame of the
Barcelona v Athletic tactical video gets a label: H (Barcelona has the ball), A (Athletic has it), D
(dead ball) or X (outside the halves). The labels come from code alone. The code in this
repository regenerates the file exactly, as described in [Reproduction](#reproduction).

## In short

- **Input.** Only the automatic tracking of the tactical video.
- **Model.** Gradient-boosted trees (LightGBM) in two stages, reading team-level features five times
  a second. A decoder then turns the chances at each moment into whole possessions.
- **Training.** Seven open German matches (IDSSE, CC BY 4.0). Each is degraded by two independently
  written noise simulators, so that clean tracking looks like automatic tracking. Nothing from the
  provided match was used to train, tune or choose the model.
- **Testing.** Three tiers of held-out matches, each used for fewer decisions than the one before.
  The last tier was 15 real automatic-tracking matches, untouched until the model was final. There
  it scored spellF1 0.614 against 0.368 for the baseline, and beat it on all 15 matches.

## How it works

### 1. Reading the tracking

The provided tracking has 46 track slots and no identities. A slot is a stretch of track, not a
person, so the model never tries to follow players. The metadata assigns every slot to a team,
with the home team (Barcelona) listed first, and every feature is summed over a team. The file is
read strictly: a malformed line stops the program instead of being skipped, because one dropped
line would shift every later frame.

### 2. Features

The match is cut into rows of 0.2 seconds, five a second. Each row gets 92 numbers, rounded to
three decimals. Directions are measured towards the goal each team attacks, which is worked out
for each half from where the teams stand.

- **Ball.** Where it is, as depth and width relative to the attack. Also its speed, whether it is
  beyond a line, whether it is seen, and how long since it was last seen and until it is next seen.
- **Ball and players.** The distance from the ball to the nearest home and away player, and how
  many of each are within 3 m. A team has *apparent control* when one of its players is within 2 m
  of a ball moving slower than 8 m/s.
- **Control across gaps.** The ball is missing on about 41% of graded frames, so the last and next
  moments of apparent control are carried across each gap. That includes which team had control
  and how long ago or ahead it was.
- **Team shape.** Each team's speed, depth, spread and how far it has pushed up. Also players in
  each box and in their own half, and the gap between the two teams.
- **Dead-ball cues from players only.** Overall pace, measured over one second so that tracker
  jitter cancels out. Also the share of slow players, how many are moving faster than 3 m/s, how
  many stand near the lines (throw-ins, corners), and the time since the half began.
- **Time windows.** Many of these are averaged over the past and over the future *separately*. The
  windows are 0.4, 1, 2 and 4 s, and 1, 4, 10 and 20 s for the slow dead-ball cues. Keeping past
  and future apart lets a model place a change between "before" and "after".

52 of the 92 features never touch the ball. These are the *player-only* features used below.

### 3. First stage: ten questions about each moment

Ten LightGBM classifiers each answer a yes-or-no question from the 92 features. All use 150
rounds, learning rate 0.06, 63 leaves, at least 200 rows per leaf, L2 penalty 5, a fixed seed and
deterministic mode.

| Question | Reads |
|---|---|
| Is the ball dead? | player-only features |
| Which team has it? (live moments only) | all |
| Is a change of label within 0.6 s? | all |
| Is a stop, a restart or a turnover within 0.6 s? (three questions) | all |
| Is the ball dead, judged with the ball in view? | all |
| Which team has it, judged from player positions alone? | player-only features |
| Which team has it 1 s from now, and which had it 1 s ago? (two questions) | all |

### 4. Second stage: the same questions across time

A single moment is often ambiguous; the pattern around it is less so. The second stage reads the
first stage's ten answers across time:

- their values from 0.2 to 5 s before and after;
- their averages over the past and the next 1 to 20 s, and the rise between the two;
- their highs and lows over the past and next 1 to 5 s;
- the time since and until the last flip in team, in dead ball and in the change chance.

That makes 211 columns. Three LightGBM heads read them and answer the final questions: is the
ball dead, which team has it, and is a change near.

The second stage must not learn to trust answers from a first stage that already saw the same
play. So its training rows are *out of fold*: the training matches are split into four groups, and
each group's first-stage answers come from a first stage trained on the other three. The first
stage used for prediction is then trained on all matches.

### 5. A ball-free partner for the dead-ball call

Most of the second stage's gain comes from better dead-ball calls, and those depend on reading the
ball. That is risky, because each tracker shows a dead ball differently. When the model was
trained on one simulator and tested on the other, a dead-ball side that read the ball collapsed:
alive-or-dead accuracy fell to 0.81, and spellF1 to 0.348 against 0.399 for the earlier model.

So the final model has a partner. The partner is trained in exactly the same way, except that its
dead-ball questions (stop, restart, dead ball and shape) read only player-only features, and its
dead-ball head reads only those answers. The dead-ball chance used is the plain average of the two
models' chances. The weight of 1/2 was fixed before any test and never tuned. Team and change
chances come from the main model. On the development matches the average kept nearly all of the
gain (within 0.01 of the full model). It also held the earlier model's level when trained on one
simulator and tested on the other.

**Both views.** For the submission the whole model runs twice: once on the match as given and once
with the two teams swapped. The second answer is swapped back and the two are averaged, so neither
team's chance depends on which one the file calls home. This needs no retraining and has no
setting to tune.

### 6. Decoding whole possessions

spellF1 rewards whole possessions, not single frames, so the chances are decoded into spells with
the Viterbi algorithm, once per half. There are four hidden states: home, away, dead after home and
dead after away. Both dead states are written as D. Splitting them lets a restart cost differ by
which team restarts.

| Switch | Cost |
|---|---|
| Turnover (home to away or back) | 2.4 |
| Stop (live to dead) | 1.2 |
| Restart by the other team | 0.96 |
| Restart by the same team | 1.44 |

Costs are in log-probability units. On top of the fixed cost, a switch costs as much more as the
change head finds it unlikely (minus the log of the change chance), so switches land where a
change is likely. Everything is rounded to integers (thousandths), so the same chances give the
same labels on every machine. A turnover costs twice a stop because the team questions alone split
real possessions too finely. The labels are then spread back from rows to video frames.

### 7. Fixed facts

- Graded frames of the second half before its kickoff, 110808 to 113741, are D. The organisers'
  FAQ states that the second half kicks off at frame 113742. The model sees the second half only
  from that frame, because every match it trained on starts each half at its kickoff.
- Frames outside the two halves are X. Inside the halves we never write X. Under spellF1 an X is
  filled with the previous label, so it gains nothing, and under macroF1 it counts as a miss.

### Why this design

- **Trees on team-level features.** They need no player identities and train well on seven
  matches. They are also fast, and deterministic with one thread.
- **A decoder of whole spells.** The metric rewards whole possessions, so stable boundaries matter
  more than frame accuracy. Fancier decoders (semi-Markov, decoding for F1 directly) gained nothing
  in our simulations once the evidence was noisy.
- **Deep temporal models were tried and dropped.** A temporal convolution network blended with the
  trees gained on simulated data. But alone it lost 0.021 on real tracking, and trained on one
  simulator and tested on the other its gain shrank to about 0.03. It also made exact reproduction
  harder.
- **Stacking replaced our first model.** Our first model (v1) had the three first-stage heads, a
  decoder and a small Smart Tagging adjustment. The current model (v2) replaced it only after
  beating it under a rule written down in advance (see [Testing](#testing-and-results)).

## Training data

None of the training data comes from the provided match, and we hand-labelled nothing on any
match. Every dataset is fetched by script at a pinned version, and none is in this repository.

| Dataset | Use | Source and licence | Who labelled it, and how |
|---|---|---|---|
| IDSSE: 7 German matches, 2022/23 (2 Bundesliga, 5 2. Bundesliga) | The only training data | [pysport/idsse-data](https://huggingface.co/datasets/pysport/idsse-data), CC BY 4.0 | Per-frame ball status and possession, supplied with DFL's official tracking and published in the dataset |
| Metrica sample games 1 and 2 | Testing only: one development match, one confirmation match. Our first model, v1, also trained on them; the submitted v2 does not | [metrica-sports/sample-data](https://github.com/metrica-sports/sample-data); no licence file, so used for testing only, never redistributed, and credited here | Derived by our code from Metrica's published event data |
| Metrica sample game 3 | Final test only | As above | As above |
| SkillCorner: 5 A-League matches, 2024/25 | Real-tracking development check | [SkillCorner/opendata](https://github.com/SkillCorner/opendata), MIT | Derived by our code from SkillCorner's phases of play |
| SkillCorner: 15 other matches | Final test only | As above | As above |

**Size.** Seven full matches at 25 frames a second. Each is seen eight times in training: two
simulators, two noise levels (0.7 and 1.3), and each copy also with the teams swapped.

**Matching the challenge's meaning of possession.** DFL's possession flips on every touch, but the
challenge says a simple touch or deflection is not a change of possession. So in every external
dataset, a spell shorter than one second between two spells of the other team is given back to
that team. The one-second limit comes from that definition. A person read the public 5-minute
window to understand what counts as possession, as the organisers allow, and saw few spells under a
second, so the limit was kept small. It was never fitted to any statistic of the ground truth.

**From clean to automatic tracking.** The training matches are far cleaner than the provided
tracking. Two simulators, written independently, degrade them:

- `src/noise.py` loses the ball in bursts, more often when it is high or crowded, with gaps of
  about 1.5 s. It replaces the provider's frozen dead ball with a slow drift to where play restarts,
  and breaks player tracks into pieces of about 20 s.
- `src/noise_b.py` models a single wide camera. Aerial balls are projected onto the grass, jitter
  grows with distance from the camera, and players are lost in crowds and come back in new slots.
  It also adds swapped tracks, brief duplicate players, and tracks filed under the wrong team.

Both remove player identities, ball height and the frozen dead ball. Neither reads labels, and
permuting the labels leaves their output byte-identical. Their settings are judgement calls,
deliberately wide, and none was measured from the provided match. While choosing these ranges, a
statistics script once read overall tracking and label figures (ball visibility, gap lengths,
label shares) from all twenty SkillCorner matches and all three Metrica games. No final-test match
was ever used to train, tune or choose a model.

## Assets used and dropped

| Asset | Decision |
|---|---|
| Tactical automatic tracking | Used; the only input |
| Smart Tagging | Used by v1 at a small weight; dropped in v2, see below |
| Homography | Not used; the tracking is already in pitch coordinates |
| Tactical and broadcast video | Not used. Output was never checked against the video |
| Broadcast tracking | Not used |
| Public 5-minute ground truth | Read by a person to understand what counts as possession. Also used to check that the official scorer, under our pinned packages, reproduces the organisers' published baseline scores (pass or fail only). Never used for training, tuning or choosing between versions |

**Smart Tagging.** Its phases name a team: attacking phases point to that team, defending phases
to the other. No other match has these tags, so we tested them on simulated tags on external
matches. For v1, a weight of 0.5 added about 0.01. For v2, every weight above zero cost 0.003 to
0.008, unless the tags were right 95% of the time, which we cannot verify. Team errors sit at
handovers, and a roughly timed phase cannot place a handover. So v2 does not use them.

**Also dropped after testing:**
- Ball-touch and likely-receiver features gained 0.010 to 0.018 on simulated noise but lost 0.011 on
  real tracking.
- Training with longer ball gaps, with wider noise levels, with simpler trees, or with slower
  learning: none beat the first model by our margin.
- Our own ball detection from video was not pursued. Even restoring every missing ball frame with
  the true position lifted the plain baseline only to about 0.27 to 0.28, so the possession logic
  matters more than ball coverage.

## Possession rules

- **Possession** belongs to the team in control of the ball. Apparent control is a player within
  2 m of a slow ball, and what the model learns comes from the providers' labels.
- **Loose balls** stay with the last team in control until the other team gains it, because control
  is carried across gaps and the training labels behave the same way.
- **Touches, deflections and challenges.** A spell under one second between two spells of the
  other team does not count, so a challenge that only touches the ball does not change possession.
  A challenge that wins the ball for longer does.
- **Dead ball** runs from when play stops until the restart. The model judges it from how the
  players behave (pace, players at the lines, formation) and, through the averaged main model, from
  the ball.
- **Restarts.** The decoder remembers who had the ball before a stoppage. A restart by the other
  team is cheaper than one by the same team, which matches how play usually restarts after the
  ball goes out. All four costs were chosen on external matches.
- **Before the second-half kickoff:** D. **Outside the halves:** X.

## Testing and results

Each tier was used for fewer decisions than the one before, so its score is harder to flatter:

1. **Development.** Five matches, each held out of training in turn: four German matches and
   Metrica 1. They were run through both simulators. Five SkillCorner matches of real automatic
   tracking, with no simulator, were also used. Every design decision was made here, with at most
   ten configurations per round.
2. **Confirmation.** Four more held-out matches (three German, Metrica 2), used once, for the
   finalist only. The rule was written beforehand: beat v1 by at least 0.02 on both simulators, with
   the interval above zero, and not be reliably worse on real tracking.
3. **Final test.** Fifteen SkillCorner matches and Metrica 3, used once after the model was fixed
   and its file had passed all checks. The rule was written beforehand: the result changes nothing
   unless v2 is reliably worse than the baseline.

Scores are spellF1. The baseline is the organisers' 2-second smoothed nearest-player rule. In
tiers 1 and 2, v1 is v1's recipe retrained without the held-out match.

| Tier | Test | v2 | v1 | Baseline | v2 minus v1 [90% interval] |
|---|---|---|---|---|---|
| Development | 5 matches, simulator A | 0.597 | 0.512 | | +0.084 [+0.071, +0.097] |
| Development | 5 matches, simulator B | 0.544 | 0.446 | | +0.098 [+0.084, +0.111] |
| Development | 5 SkillCorner matches, real tracking | 0.654 | 0.618 | 0.414 | +0.036 [+0.020, +0.051] |
| Confirmation | 4 matches, simulator A | 0.598 | 0.515 | | +0.083 [+0.068, +0.097] |
| Confirmation | 4 matches, simulator B | 0.557 | 0.453 | | +0.104 [+0.088, +0.118] |
| **Final** | **15 SkillCorner matches, real tracking** | **0.614** | **0.577** | **0.368** | **+0.037 [+0.028, +0.045]** |
| **Final** | **Metrica 3, simulator A** | **0.662** | **0.593** | **0.266** | **+0.069 [+0.045, +0.094]** |
| **Final** | **Metrica 3, simulator B** | **0.598** | **0.537** | **0.241** | **+0.061 [+0.039, +0.089]** |

- **Intervals.** They come from a paired bootstrap over 90-second blocks of play, 1,000 draws,
  5th to 95th percentile.
- **Final test.** v2 beat the baseline by +0.246 [+0.234, +0.258] and beat both the baseline and
  v1 on every one of the 15 matches.
- **Both views.** The table scores a single pass. Averaging both views, as the submission does,
  was measured afterwards on development matches only: +0.008 [+0.002, +0.014] on the five
  SkillCorner matches, and -0.001 and +0.006 on two matches under each simulator. The final test
  was not rerun.
- **Tuning.** The decoder's turnover cost was chosen after seeing the development real-tracking
  scores, so the 0.654 is lightly tuned. The final test was not.

**These are not forecasts of the score on the provided match.** SkillCorner tracking comes from
broadcast video with a filled-in ball, and its labels are SkillCorner's own, so even the baseline
scores differently there. On the provided match we only ran automatic checks that print pass or
fail, and all passed:
- the file is valid, and identical when written twice;
- X falls exactly outside the halves, and the frames before the second-half kickoff are D;
- possessions per minute, dead-ball share and team share fall within wide bounds taken from the
  open matches, which would catch a broken file;
- the team calls broadly agree with Smart Tagging's, which would catch home and away being swapped.

## Limitations

- **The noise is simulated.** We could not measure how the provided tracking fails, so we trained
  across a wide range. The real failures may differ.
- **Very short possessions are mostly missed.** On external matches the model predicts fewer
  possessions than the truth, and spells under two seconds are rarely recovered.
- **Team calls weaken in long ball gaps,** where only player shape is left to go on.
- **Label conventions differ.** Training labels are DFL's, adjusted by one rule, while the
  challenge's truth comes from Metrica's corrected tracking. On our tests, moving between providers'
  labels cost at most about 0.02, but the provided match's conventions may differ further.
- **The dead-ball call still partly reads the ball.** A tracker whose dead ball behaves in a way
  neither simulator imagined could mislead the main model. The ball-free partner limits the damage
  but does not remove it.
- **With more time** we would run a real tracker over open video with trusted labels, and learn the
  noise from data instead of simulating it. We would also train on more matches.

## Reproduction

You need [uv](https://docs.astral.sh/uv/) and the match bundle unpacked into `data/` (or set
`MTAH_DATA_DIR` to its folder), as `games.py` explains. Python 3.11 and every package are pinned in
`uv.lock`.

```bash
uv sync
uv run python -m src.submit       # writes evaluation/results/827.csv from the saved weights
uv run python evaluation/validate_submission.py evaluation/results/827.csv
uv run pytest                     # 344 tests; none reads the provided match
```

The SHA-256 of our `827.csv` is
`71c0d0837faa7334a0d719a0b8c702f7bf5611cf905720673d7a3c6d3f5bf89b`.

Regeneration reads the trained weights in `models/v2` (27 MB, committed), because LightGBM promises
repeatable training only on the same system. Prediction runs on one thread, features are rounded,
and the decoder works in integers, so the saved weights give the same file on any machine.
Changing every input position by one part in a billion changed no labels on our test matches. On
Windows, `.gitattributes` stops Git from changing the weights' line endings on checkout, and the
loader accepts either line ending.

To retrain the weights from the German matches only (about 45 minutes on one thread):

```bash
uv run python -m src.external.idsse download
uv run python -m src.external.idsse cache
uv run python -m src.train_final  # writes models/v2
```

Retraining on another machine may not reproduce the weights byte for byte.

The test results above come from `src/challenge.py` (development and confirmation) and
`src/final_test.py` (final test). They also need the Metrica and SkillCorner data:

```bash
uv run python -m src.external.metrica download
uv run python -m src.external.metrica cache
uv run python -m src.external.skillcorner download
uv run python -m src.external.skillcorner cache
uv run python -m src.final_test
```
